## Alignment Note (added 2026-08-10)

This table is cross-checked against `NDC_Integration/SPEC.md` and the live V2 Postman collection JSON, and against `NDC_Integration/Resources/SeatMap QC Execution Checklist.md`. Flagged rather than silently resolved:

- **TC-INT-FC-001/002/003** describe passing seat data ("Select seat 1A ... Pass seat data to FareConfirm request") into **FareConfirm**. The directly-inspected V2 Postman collection shows FareConfirm has no seat-related field at all — only **Book** carries `passengersSelectedSeats` (SPEC.md §2.2, §2.9). Either these three rows use "FareConfirm" loosely to mean "the booking-confirmation step" (i.e. Book), or they describe an aspirational/different design not present in the current collection. Treat as `UNKNOWN` — confirm which endpoint actually receives the seat data before executing these three as written, rather than assuming FareConfirm's contract silently grew a seat field.
- **TC-INT-BOOK-001/002/006** use the term `passengersBookedSeats` for the Book **response**. The directly-inspected collection uses the identical field name `passengersSelectedSeats` on **both** the request and the response (SPEC.md §2.9) — `passengersBookedSeats` does not appear anywhere in the collection JSON. Treat `passengersBookedSeats` in this table as this document's own descriptive/colloquial term, not a literal API field name, unless confirmed otherwise live.
- None of the rows below cover the new `SeatAfterHold` endpoint or the Hold branch's seat-attachment mechanism at all — see the new rows appended below and SPEC.md §2.7a.
- Corresponding automatable test cases for the rows below are tracked in `NDC_Integration/TestCases/SeatMap_TestCases.csv`, cross-referenced inline where a direct mapping exists.
